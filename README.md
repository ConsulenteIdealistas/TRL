# TRL投資分析システム

技術・企業の**長期成長評価（long）**と、1〜6か月の**イベント評価（event）**を分離して扱う分析基盤です。
公開情報（論文・治験・ニュース・開示・財務）を収集し、LLM が根拠を抽出・採点して SQLite に保存、GitHub Pages で表示します。
根拠・出典・不足情報を必ず保存し、情報不足の候補は**保留（hold）**にして点数を出しません。
Python 標準ライブラリのみで動作し、運用はスマホのブラウザだけで完結します。

> スコアは評価尺度です。株価上昇確率・成功確率・投資利益率ではなく、売買の自動判定にも使えません。投資助言ではありません。

公開サイト: https://consulenteidealistas.github.io/TRL/ （画面と `data.json` は公開されます）

## 全体像

```
収集 (ソース別に並列) → 正規化・重複排除 → 企業リンク付け → スクリーニング
  → 選定 (コア企業リンク・材料の強さ順, 評価上限は実行ごとに指定)
  → LLM抽出 (根拠・事実) → LLM評価 (long / event)
  → SQLite 保存 (dataブランチ) → サイト書き出し (data.json + web/) → 翻訳 (表示対象＋ウォッチ一次情報のキュー)
  → 古い材料の削除 (prune)
```

- **保持ポリシー (prune)**: DB が単調に増え続けないよう、実行の最後に古い材料を消します。対象はプール専用の材料と除外済みに限ります（ニュースは公開から180日超、財務は800日超、除外済み候補は180日超、抽出キャッシュは180日超）。評価が付いた候補と未解決のレビューキューにある候補は消しません。保持期間は利用側の窓（ニュース90日・財務400日）の2倍に取ってあります。キー形式の移行で生じた旧形式の Yahoo 財務レコードは、新形式の同企業・同時期レコードがある場合に限って消します。手動実行は `trl.py prune`。

実行は GitHub Actions のワークフロー `.github/workflows/main.yaml` が担います（後述「実行と運用」）。

## 企業辞書（entities/）

企業は市場別ファイル（`entities/jp.json`, `us.json`, ... 全27ファイル）に1エントリずつ定義し、起動時に合体します。企業追加は該当ファイルへの1エントリ追加で完結します。

エントリの主な項目:

| 項目 | 内容 |
|---|---|
| `id` / `name` / `aliases` | 一意なID、正式名、別名（日本語名含む）。別名は3文字未満・他企業との衝突を検証で拒否 |
| `ticker` / `exchange` / `market` | 証券コード（接尾辞なし）、取引所、市場コード（US/GB/...、JP は省略可）。ticker の形式も検証する |
| `sector` | `bio` / `space` / `semiconductor` / `ai` / `robotics` / `energy` / `quantum` / `defense`（主分類は1社1つ） |
| `tags` | 分野を跨ぐ第二の分類（複数可、表示・分析専用で評価には使わない）。`photonics`（光通信）と `medtech`（医療機器）に加え、技術テーマ別の語彙（地球観測・量子コンピュータ・創薬AI・パワー半導体・蓄電ESS 等。ラベルは `web/app.js` の `TL`）と、他分野の sector キー（例: 半導体寄りのロボティクス企業への `semiconductor`）を使う。重なりは具体的なタグを優先し、包含関係にある汎用タグ（例: `industrial_robotics`）は付けない |
| `tier` | `core` / `watch` / `reference`（後述） |
| `stage` | 企業の段階: `rd`（研究開発型）/ `demo`（実証型）/ `production`（量産型）/ `commercial`（商業化型）。サイト表示と分析専用で、評価・選定には使わない |
| `watch.news_name` | ニュース検索に使う代表名 |
| `watch.sponsor` | ClinicalTrials.gov のスポンサー名（ある企業のみ治験クエリを生成） |
| `watch.pubmed` | PubMed 所属検索文字列（ある企業のみ） |
| `watch.openalex` | OpenAlex 機関ID（登録済み14社のみ） |
| `watch.extra_keywords` | 製品名・技術名などの追加キーワード |
| `products` | 製品リンク用の製品名・別名（任意） |

**tier の意味**: 評価の対象は**コア企業にリンクする候補のみ**です。ウォッチ企業は収集と根拠プールには参加しますが、その企業だけに紐付く材料は評価されません。**参考（reference）**は収集はウォッチと同じですが、評価対象にも昇格候補にもならず、比率の上ではウォッチの内数として数えます。層の移動は `tier` の書き換えだけです。

**クエリの自動生成**: 企業クエリは `sources.json` には書かず、辞書の `sector` と `watch` から起動時に自動生成します（`trl.py queries` で確認可能）。

- `gnews`: 代表名 + セクター別キーワード集合（市場別ロケール・言語別キーワード集合あり）
- `prtimes`: 英日表記の引用符付き企業名（**JP のみ**）
- `trials`: `sponsor` がある企業のみ
- `yahoo`: `ticker` + 市場別接尾辞（GB=.L / DE=.DE / CH=.SW / IN=.NS / HK=.HK / TW=.TW など市場ルールで定義、US はなし）
- `edinet`: 証券コード（**JP のみ**）
- `pubmed`: `watch.pubmed` がある企業のみ所属検索。その他の論文はトピッククエリ（`sources.json` の `topics`、3件）で収集
- `openalex`: 機関IDがある企業のみ

市場別ルール: EDINET・PR TIMES は JP のみ、EDGAR は US に加えて `edgar_ticker`（米上場ティッカー）を明示した 20-F 提出企業。財務数値の金額単位は報告通貨で表示します。

## 情報源と役割

| ソース | 内容 | 役割 |
|---|---|---|
| `pubmed` | 論文（所属検索＋トピック） | 評価対象 |
| `arxiv` | 論文（トピック） | 評価対象 |
| `openalex` | 企業所属の論文（抄録を復元） | 評価対象 |
| `trials` | ClinicalTrials.gov の治験（スポンサー検索） | 評価対象 |
| `gnews` | Google News RSS（企業名＋ビジネス語） | **プール専用**（評価対象にしない） |
| `prtimes` | PR TIMES の企業発表（JP のみ） | **プール専用** |
| `yahoo` | Yahoo Finance の財務（四半期ごとに1件） | **プール専用** |
| `edinet` | EDINET 開示・財務数値（JP のみ） | **プール専用** |
| `edgar` | SEC EDGAR の財務数値（XBRL、US＋20-F 提出企業） | **プール専用** |
| `roic` | ROIC.ai の財務数値（年次、キー登録時のみ・財務の穴埋めと裏取り） | **プール専用** |
| `simfin` | SimFin バルク CSV の財務数値（US/DE/CA の四半期・TTM、キー登録時のみ・財務の穴埋めと裏取り。無料バルクは遅延つき） | **プール専用** |

ソース別の取得期間（lookback）: trials 180日 / yahoo・edgar 400日 / prtimes 90日 / pubmed・openalex 365日 / edinet 45日。その他は既定30日・最大20件。浅い日（後述）は発見系ソース（pubmed / trials / openalex / prtimes / edinet）の窓を4日に切り詰めます。

### 収集と候補管理

- **重複排除**は安定IDのみで行い、タイトル類似では統合しません。キーは DOI / PMID / arXiv ID / URL。例外として Yahoo・EDGAR は URL が銘柄・企業ページ（四半期で不変）のため、四半期ごとの `source_id` をキーにします（Yahoo は市場接尾辞つきシンボル-期間。接尾辞なしだと市場違いの同名ティッカーで衝突するため）。
- ニュースは企業に紐付かないものを収集段階で捨て、転載・定型ページ・値動きまとめを媒体/タイトルフィルタで落とします。
- 候補は抄録の最低文字数（通常200字、news/disclosure は30字）と最大経過日数（365日）でスクリーニングします。
- 基準日（`--as-of`）より後の資料は評価対象外です。

### 根拠プール（評価への同梱）

ニュースと財務は単体では評価せず、同一企業の論文・治験を評価するときに根拠としてプロンプトへ同梱します。

- **関連事業ニュース**: 同一企業（製品リンク経由を含む）の直近90日・最大8件。出典の種別（origin=企業発表 `prtimes` / 報道 `gnews`）を付け、両方で確認できる事実は信頼度を高く、企業発表のみの事実は割り引くようプロンプトで指示します。
- **関連財務根拠**: 財務数値を含む開示のみ、直近400日・最大2件。論文・治験の抄録に存在しない売上・利益・現預金などの公表数値が `financial_sustainability` / `monetization` の根拠になります。実働ソースは Yahoo Finance・EDINET・SEC EDGAR で、ROIC.ai（`ROIC_API_KEY` 登録時）が年次財務の穴埋めと裏取りを、SimFin（`SIMFIN_API_KEY` 登録時）が US/DE/CA の四半期・TTM 財務（バルク CSV を市場ごとに一括取得し対象社分を抽出。無料バルクは遅延つきのため履歴の穴埋めが主）で補います。補完収集（ROIC / SimFin）の対象は財務ゼロの企業 → Yahoo のみの企業の順で、成功（1件以上取得）したら30日休み、0件・失敗は休止に入らず次回再試行します。
- **財務系の取得間隔**: 財務は四半期単位でしか変化しないため、毎回は取りに行きません（実行統計の `financial_skipped` に数えます）。EDGAR・EDINET は前回の取得成功から20日以内の企業のクエリを休みます。Yahoo は決算周期に合わせ、保存済みの最新決算の期末 +97日（次の四半期末 + 発表が始まる目安）を過ぎた企業だけを取りに行きます（期末の記録が無い企業は発見のため20日間隔）。失敗したクエリは成功として記録されないため間隔の対象にならず、次回も試行されます。あわせて Yahoo・EDINET の取得はコア企業のみです（ウォッチ企業の財務は評価対象にならないため）。
- Google News の記事 URL は直接開けない仕様のため、サイトでは記事タイトルをタイトル検索リンクに、媒体名を媒体サイトへのリンクにして表示します。

## 評価仕様

### long（長期成長評価）: 6項目・100点

| 項目 | 配点 | 軸 |
|---|---|---|
| technology_readiness | 30 | 技術軸 |
| technological_advantage | 15 | 技術軸 |
| monetization | 20 | 事業軸 |
| market_growth | 15 | 事業軸 |
| financial_sustainability | 10 | 事業軸 |
| moat_durability | 10 | 事業軸 |

必須項目は technology_readiness と monetization です。

- **総合点は6項目すべてが非nullのときのみ確定**します。1つでも null なら hold で、重みの再配分はしません。
- **例外（二軸化）**: `trl_level` が確定し **3以下**のとき、事業軸は「段階未達（pre_stage）」として不足に数えず、技術軸の2項目が揃えば技術軸の総合点（`total_scope=technology`）で final にします。前商業段階では事業項目の「存在しない」を「不足」と同一視しないための仕様です。
- 各項目には根拠（evidence）・理由が必須で、不足がある場合は不足情報（missing_info）の記録が必須です。

### trl_level と採点基準の3原則

`trl_level`（1〜9 または未確定）は technology_readiness の点数から換算せず、専用項目として判定させます。セクター別（バイオ/AI/半導体/宇宙）の詳細基準をプロンプト `long.v1.md` に埋め込んでいます。

1. **商用展開と TRL の分離**: TRL は「実環境で意図通り動作するかの実証段階」のみで判定します。販売・課金・顧客数・売上・量産規模は TRL の根拠にせず、事業軸（monetization）で扱います。
2. **「複数」「継続」の扱い**: 件数・期間は資料に明記された分のみを使い、推測で補いません。TRL 9 には繰り返し・継続の証拠が必須です。
3. **TRL と成長余地の分離**: TRL の高低から収益化・市場成長・競争優位性を推論しません（事業軸で別途評価します）。

### 材料の方向性（direction）

long 評価では、点数・TRL とは独立に「その資料が示す出来事の方向」を positive / negative / mixed で理由つきに判定します。治験中止のように全項目に点が付いても逆風の材料を誤読しないためで、サイトのカードにバッジ表示し、一覧で絞り込みできます。

### 不足情報の扱い

- 資料群に原理的に存在しないもの（第三者の市場統計・競合の定量比較・特許明細・将来ガイダンス）は不足として数えません。market_growth は患者規模などの代理指標で、財務は既存数値で評価します。
- 時間待ちの不足（治験結果の公表待ちなど）は接頭辞「結果待ち：」で区別し、サイトでは別掲します。
- 治験レジストリ側で要旨が更新された候補は `material_updated_at` を記録し、再評価の間隔を待たずに優先再評価します。

### event（イベント評価）: 6項目・100点

| 項目 | 配点 |
|---|---|
| catalyst_quality | 25 |
| expectation_gap | 25 |
| not_priced_in | 20 |
| timing_feasibility | 10 |
| supply_demand | 10 |
| downside_resilience | 10 |

長期とイベントは別々に評価・保存し、平均しません。市場予想が確認できないイベントは分類を確定せず、expectation_gap / not_priced_in を null に戻して保留にします。

**株価反応データ（2026-11-06 導入、プロンプト event.v2）**: event 選定された候補には、Yahoo の日次バーから決定的に計算した株価反応を材料として同梱します（アンカー材料の反応 [0, +1]、頑健なばらつきで割った標準化反応 z、事前ドリフト、出来高倍率。系列は `market_series` にキャッシュし、選定企業だけ遅延取得）。市場予想の記述が無くても、測定可能な反応があれば expectation_gap / not_priced_in を判定してよいことにし、コード側の強制 null も反応がある場合は外しています。導入前の hold は自動では再評価されません。

### スコアのバンド

| 点数 | バンド | 意味 |
|---|---|---|
| 80–100 | very_strong | 非常に強い |
| 60–79 | strong | 強い |
| 40–59 | moderate_uncertain | 中程度・不確実 |
| 20–39 | weak | 弱い |
| 0–19 | extremely_weak | 極めて弱い |

### 選定と再評価

- 選定の優先順位: 企業リンクの強さ（strong > weak）> 実証シグナル > 新しさ。1回の評価上限は実行ごとに指定します（定期実行は5件/回）。
- 評価は4件並列（結果の保存と打ち切り判定は候補順）。評価フェーズには時間予算600秒、実行全体には締め切り（run_budget 1320秒）があります。
- hold の再評価は14日後から。ただし材料の更新が前回評価より新しい候補は間隔をバイパスします。再試行は最大3回まで。
- **未評価のみモード**（`--only-new`）: 一度でも評価された候補を除外し、未評価の候補だけを対象にします。
- LLM API の失敗（429・5xx・タイムアウト・認証エラー等）は評価結果として保存せず、候補を未評価のまま残します。連続2回失敗したら評価フェーズを打ち切ります。内容起因の失敗（不正な JSON 等）は error として保存します。旧版が API 失敗をエラーとして保存した候補は、画面・レポートのどちらにも表示しません。
- 抽出結果は入力ハッシュ（基準日を含む）が同じなら再利用します。

### LLM 設定

- プロバイダは Gemini のみ（未設定・空のときも `gemini` として動作し、`none` と明示したときだけ収集のみになります）。呼び出しはタイムアウト120秒、再試行1回。429 は再試行せず、次の段へ進みます（枯れた枠への聞き直しは時間と枠の両方を無駄にするため）。
- 主モデルが一時的な失敗（503/429 等）を返したときだけ、代替モデルへ降ります。階段は Gemini 内の2段（主 → `TRL_LLM_FALLBACK_MODEL`）です。恒常的な失敗と時間上限では降りません。段ごとに連続失敗の見切り（ブレーカー）があり、主と代替1は1回失敗した時点でその実行中はその段を飛ばします（最終段は飛ばしません）。候補1件あたりの総時間予算は300秒（`llm.candidate_budget_sec`）で、失敗の連鎖が1件を際限なく長引かせることはありません。モデルが廃止・変更されたときは、コードを触らず Variable の書き換えだけで切り替えられます。
- 呼び出しは試行単位で `llm_calls` に記録します（候補・目的・実際に答えたモデル・所要秒数・成否・トークン数）。どのモデルが評価したかはサイトにも表示します。
- プロンプト: `extract.v1.md`（抽出）/ `long.v1.md`（長期）/ `event.v2.md`（イベント。v1 は凍結）。
- 監査は規則ベースに一本化しています（`trlcore/audit.py` の決定的チェック A1〜A15 と event 監査 E1/E2: 件数・継続の主張と根拠の照合、TRL 9 の継続証拠、成長推論の構文、技術と商用の混同、欠落判定の妥当性、減点理由の具体性、反証の欠落、根拠のない高得点、公開日と基準日の不整合、理由中の数値の原文照合、出典リンクの形式、総合点の再導出照合、弱い企業リンクのみの確定、TRL 9 の証拠不足に対する上限の観測、実測した価格反応との整合）。LLM 監査は廃止しました。監査は点数を動かさず「要確認」として記録し、サイトの監査ページで処分します。監査の要項（8分類と LLM の役割分担、GAO TRA Guide や ISA 500/520 を出典とする定め）は別途定めています。

## サイト（web/）

- 書き出し対象は「各候補の最新評価＋未評価のうち次回評価予定＋除外候補（理由つき）」。データ形式は `data.json`（schema_version 3）。体裁の詳細は次節「公開形式」。
- 一覧: 検索（2文字以上で企業名・キーワード・タイトルの**サジェスト**、日本語入力・スマホ対応）、国・市場と分野とタグと段階の絞り込み、方向性フィルタ、並び替え（おすすめ順 / TRL 高い順・低い順 / 国・市場別 / 分野別 / 日付の新しい順・古い順）。
- 表示状態: 選定可能（final）/ 要追加調査（review）/ 保留（hold）/ 評価待ち（pending）/ エラー / 除外。画面側で点数の再計算・換算・平均はしません。総合点は「総合点（長期）」と「イベント評価（短期）」を分けて表示します。
- 詳細ページ（`detail.html`）: 根拠の全文、反証、不足情報と「結果待ち」の別掲、イベント評価、同梱した関連ニュース・財務根拠を表示します。
- 論文には「要点（抄録から抽出）」を表示します。抄録（5文以上）から文のスコアで上位3文を原文順に抽出する決定的な処理で、書き出し時に計算します（LLM・API は使いません）。
- ウォッチ・参考ページ（`watch.html`）: 評価対象外の監視企業320社のプール材料を企業単位で読むページ。一次情報（上限15件）とニュース（上限5件）を出典リンク・出典コピー・リンクコピー付きで表示し、タグ絞り込みはセクター別の折り畳みグループです。
- 採点基準ページ（`criteria.html`）: 現行の配点・必須項目・バンドと評価規程の全文。監査ページ（`audit.html`）: 規則監査の「要確認」を処分し、再評価予約と TRL 調整を入力するページ（調整は非破壊の別層）。
- 外部由来のテキストは全てエスケープして描画し、リンクは http/https のみ許可します。スコアは数値以外を表示しません。

### 翻訳

タイトル・抄録の日本語訳は表示対象のみ作成して DB に保存し（1回訳せば再利用）、画面で日本語訳/原文を切り替えます（未訳のものは原文のまま表示）。翻訳は専用 API のみで行い、評価用 LLM には任せません。

1. **Azure Translator**（本命: 無料枠 F0 が月200万字・毎月リセット）
2. **DeepL API**（合計100万字の一回限りの枠のため温存）
3. **Google Cloud Translation**（月50万字まで無料・毎月リセット、二重障害時のみ）

キーが無い段は自動で飛ばします。どの経路で訳したかは候補ごとに記録され、画面にも「訳: Azure」のように表示されます。

表示対象とは別に、ウォッチ・参考企業の一次情報（論文・治験のみ、ニュースは対象外）を翻訳するキューがあります。優先順は 表示セット > ウォッチ > 参考 > コア で企業をローテーションし、1回50件まで、月次予算150万字です。経路は Azure → Google で、温存中の DeepL は使いません。

翻訳に使った文字数は段ごとに数えて run 記録に残します（`translation_chars`）。累計（Azure / Google は月次、DeepL は一回限り枠のため通算）が 50万 / 100万 / 125万 / 150万 / 175万 / 200万字のしきい値を跨ぐと、run 記録に `translation_alerts` として残し、実行ログにも警告を出します。

## 公開形式（サイトと data.json の体裁）

公開サイトと `data.json` の読み方です。画面は `data.json` の値をそのまま表示し、画面側で再計算・換算・平均はしません。

### 表示状態と統計

| 表示 | 意味 |
|---|---|
| 選定可能（final） | 必須項目が揃い、総合点が確定した評価 |
| 要追加調査（review） | 項目は揃ったが追加の確認が要る評価 |
| 保留（hold） | 必須項目の不足があり、総合点を出していない評価。詳細に主因（対象企業を特定できない / 根拠が資料に無い）を併記 |
| 未評価（pending） | まだ評価していない候補。統計では「うち次回予定」を併記（次回評価予定は未評価の部分集合） |
| エラー（error） | 内容起因で評価が成立しなかった候補 |
| 除外（rejected） | 関連性スクリーニングで落ちた候補。評価は行われていない。一覧には状態フィルタで「除外」を選んだ時だけ現れる |

統計は8枠（掲載中 / 選定可能 / 要追加調査 / 保留 / 未評価 / エラー / TRL判定済み / 除外）。「TRL判定済み」は状態ではなく、TRL レベルが確定した評価の横断数です。掲載中には「うち前回比あり」を併記します。

### 数値の読み方

- **TRL**: 1〜9 または未確定。技術成熟度スコアからの換算はしません。根拠付きで判断できた場合だけ表示します。
- **総合点**: 現在の表示値は、保存済みの項目点から**現行の重みで再計算した値**です。重みが改訂されても項目点は変わりません。評価した当時の総合点と違う場合は、詳細に「評価当時の総合点」を併記します（`data.json` では `total` / `band` が現行値、`total_orig` / `band_orig` が当時の値）。
- **前回比**: 一覧では TRL と総合点の変化だけを短く出し、項目点の変化は詳細に置きます。TRL の昇降だけに色と矢印を付けます。
- **材料の方向性**: 点数・TRL とは独立の判定で、バッジ表示します。
- **出典の表記**: カードに「評価: モデル名」（実際に採点した LLM）、日本語訳には「訳: Azure」のように翻訳経路を表示します。
- **段階（stage）とタグ**は表示・分析専用で、評価や選定には使いません。

### tier の4層（導出レイヤー）

- 辞書の tier（core / watch / reference）は不変で、その上に企業ごとの**導出 tier**（`derived_tier`: `core` = Core / `conditional` = Conditional / `look` = Look / `see` = See）を併記します。導出は辞書・評価・監査・処分から決定的に計算する別層で、元の値には触りません（ルール版は `tiers/v1`）。
- 基礎 watch → Look、基礎 reference → See。基礎 core は「最新の帰属可能な long 評価がある」「その評価の企業リンクが strong かつ一意」「その評価の最新の監査結果に未処分の要確認が無い（誤検知と処分された flag は数えない）」の全てを満たせば Core、1つでも欠ければ Conditional です。判定に使うのは最新の long 評価のみで、event 評価だけの企業は Conditional になります。
- `summary.tiers` には4層の分布（社数・シェア）、目標（Core 100 / Conditional 150 / Look 200 / See 50社 = 20/30/40/10%。比率は目安）との差、シェアが目標から ±5pt を超えた層の**警告**が入ります。警告は出すだけで、層の自動調整はしません。実行レポートにも同じ分布と警告が出ます。
- 各企業には `derived_reasons`（未充足の条件の理由文。導出側の文面そのまま）も併記され、サイトでは Conditional の企業に理由を平文で表示します。主ページには分布と警告の帯と「企業の層」の絞り込みがあり、監査ページのカードにも層を併記します（表示の差は検証状態とその理由だけに対応させ、状態色は使いません）。
- 導出結果は export のたびに DB の `tier_snapshots` へ追記のみで記録され、過去の層を後から再現できます。
- 評価の選定対象は従来どおり基礎 core（= Core + Conditional）で、導出 tier は選定に影響しません。

### 絞り込みと端末内の機能

- 絞り込みはチップの複数選択です（グループ内は OR、グループ間は AND、空は「絞らない」）。TRL はレベルチップ＋範囲入力で、「判定済み」チップは 1〜9 全選択への近道です。
- 調査メモ・注目ピン（★）・新着バッジは**端末内の機能**です。サーバには送らず、その端末のブラウザにだけ保存されます。新着は「前回その端末で開いた時より後に付いた評価」につきます。注目ピンは共有リンク（`?pins=`）で別端末へ持ち運べます（統合のみで、上書きはしません）。
- コピーはブラウザ内で完結します: 研究概要の原文 / 日本語訳、出典（題名・出典名・日付・URL）、評価まるごと（項目点・理由・TRL・不足・前回比）、カードからの出典 / 詳細リンク。

### 非破壊の約束

- 評価は追記のみで、過去の評価の項目点と TRL は書き換えません。変わるのは重み改訂時の総合点（集計値）だけで、当時の総合点は固定して残します。
- 材料（治験・開示）が出典側で書き換わった場合は、上書きする前の版を DB 内に残します。
- 削除は保持ポリシー（prune）の範囲だけです。保持期間には規則があります（利用側の窓の2倍: ニュース180日 / 開示800日 / 除外180日）。評価が付いた候補は消しません。

## 実行と運用

### ワークフロー（.github/workflows/main.yaml）

- 定期実行: **火〜金曜 06:30 JST**（cron `30 21 * * 1-4` UTC）。火曜は「深い日」として全期間の窓で収集し、他の曜日は「浅い日」として発見系ソースの窓を4日に切り詰めます。定期実行の評価上限は5件/回（週20件）。手動実行も可（深さは入力で選択）。同時実行は1本のみ、タイムアウト30分。
- 補助ワークフロー: `site.yaml`（サイトだけを最新 DB から書き出してデプロイする。UI の変更を数分で反映するため）、`compare.yaml`（モデル比較専用。評価本体には触れない）。
- 処理の流れ: テスト → data ブランチから DB 復元（`--depth 1` で取得）→（任意で purge）→ パイプライン実行 → サイト書き出し → DB を data ブランチへ保存 → GitHub Pages へデプロイ。
- DB は `data` ブランチの `trl.sqlite`（ルート直下）に保存され、実行ごとに通常のコミットで履歴が残ります。レポートは `data` ブランチの `reports/latest.md` と Actions の Summary でも読めます。
- DB が壊れた・消えた場合の復旧手順は [RECOVERY.md](RECOVERY.md) にあります（data ブランチの履歴から良品を取り出して戻す手順）。

手動実行の入力:

| 入力 | 既定 | 内容 |
|---|---|---|
| sources | 全ソース（チェックボックス） | 収集するソースの組み合わせ（ソースごとに on/off） |
| kinds | long | 評価種別（long / event / long,event） |
| max_eval | 5 | 1回の評価上限 |
| depth | deep | 収集の深さ（deep=全窓 / shallow=発見系ソースの窓を4日に切り詰め） |
| retry_failed | no | 失敗した評価の再試行（no/yes/force） |
| purge_evaluations | no | yes で評価とキューを全削除し候補を未評価に戻す（削除→再評価→再出力が1回の実行で完結） |
| only_new | no | yes で未評価の候補のみ評価 |

> **コードを修正した後は「Re-run jobs」ではなく「Run workflow」から新規に実行すること。** Re-run は元の実行時点のコミットのまま動くため、修正が反映されず、設定ハッシュも古いままになります。新規実行では `[run]` 行の設定ハッシュが最新の設定と一致するかで反映を確認できます。

## 既知の制約・設計判断

- **EDINET は運用中**: JP のコア企業の開示を取得し、財務書類（有報・四半期・半期とその訂正）からは各社直近2件まで数値を抽出して財務プールに入れます（type=5 の CSV を優先し、取れなければ type=1 の XBRL）。日次リストは直近45日分を証券コード別の索引にまとめて全クエリで共有します（クエリごとの全件走査はしません）。キー未設定の環境では取得を自動でスキップし、エラーにしません。
- **Yahoo Finance は非公式 API**（キー・登録は不要）。bot 判定を避けるため User-Agent はセッションごとに実在ブラウザの候補から選び、全リクエストをプロセス全体で最小1秒間隔に直列化します。銘柄自体が存在しない企業は取得できません。通信が2回とも失敗した場合は空結果で握りつぶさず、収集の失敗として実行統計（sources_failed）に記録します（EDGAR も同様）。
- **SEC EDGAR は公式 API**（キー・登録は不要、US 上場のみ）。company facts（XBRL）から売上・利益・現預金・短期有価証券などを抽出し、Yahoo と同じ財務プールに入れます。2026-10-29 の実測では US 94社中87社で取得でき、残り（上場直後で未提出・IFRS の集計概念が無い等）は Yahoo 側でカバーします。SEC の fair access 方針に従い User-Agent に運用者名と連絡先を含め、リクエストを間引きします。
- **arXiv は所属情報を取得しない**ため、企業との strong 一致は成立しません（現時点では対象外として扱います）。
- **OpenAlex は機関ID登録済みの14社のみ**が対象です。機関レコードが無い企業は PubMed/arXiv 側で拾います。
- **event 評価の限界**: 株価反応データは導入済みですが、市場コンセンサス予想そのものは材料にありません（反応は「予想との差」の代理として扱います）。導入前の hold は自動では再評価されず、必要なら再評価キューで拾います。
- **TDnet は見送り済み**: 公式 API は索引のみで高額、本文は PDF 中心で現在の構成（標準ライブラリのみ）では抽出できないため採用していません。
- **未実装**: 特許・IR 資料の本文解析、過去イベントの事後検証、AI 採点の妥当性検証。財務補間の残り1社（Alpha Vantage。キーは登録済み）、ESEF 収集器（EU+英国119社、導入決定済み）、スイス10社の EQS + GlobeNewswire 収集器（採用決定済み）は実装待ちです。
- 失敗した情報源は Actions ログの `::warning::` とレポートに表示されます。全情報源が失敗したときだけジョブが失敗します。
