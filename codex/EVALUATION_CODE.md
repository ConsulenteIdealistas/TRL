# TRL 評価規程（v0.4）

本規程は、TRL 投資分析システム（以下「本システム」）の評価規則の正本である。
パイプラインが実際に使う規則と、読者が読む規則を同一にする（ホワイト
ボックス化）ため、評価プロンプト・集計コード・設定ファイルは本規程に
従い、本規程と食い違う場合は本規程を正とする。

- 状態: v0.3（2026-11-10、凍結バッチ A1〜A10 を反映: claim 共通封筒・
  技術ごと TRL・時点/状態/関係・数値/識別子・facet・トレーサビリティ・
  event 構造化・防衛附則・コード語彙。プロンプトは extract/long/event
  の v3、config_version は 2026.11.2）。正本は本ファイル
  （repo 内 codex/）とし、workspace 側は控えとする（C-2）。未確定事項は
  [要確定] と明記する。
- 数値の正本: 重み・帯域・ゲート日数などの数値は `scoring.json` を別表とし、
  本規程はその意味と導出のみを定める。ただし第5章の重み表は導出過程を
  示すためのもので、効力は scoring.json の値が持つ。

---

## 第1章 総則

### 第1条（目的）
本システムは、公開資料から得られる根拠のみを用いて、企業の技術の立証段階と
事業化の進展を分けて評価し、その根拠ごと公開する。評価は投資の助言では
なく、資料の読み解きの記録である。

### 第2条（3原則）
1. **商用展開と TRL の分離**: TRL は「技術が実環境で意図通り動作するか」の
   実証段階のみで測る。販売・課金・顧客数・売上・出荷規模は TRL の根拠に
   せず、事業軸（収益化）で扱う。
2. **「複数」「継続」の統一**: 件数・期間は資料に明記されたものだけを使う。
   TRL 9 には「繰り返し・継続」の証拠を必須とするが、必要な回数・期間は
   セクターごとに定める（第3章附則）。
3. **TRL と成長余地の分離**: TRL の高低から収益化・市場成長・競争優位性・
   成長余地を推論しない。それらは事業軸の各項目で別途の根拠により評価する。
   MRL・CRL（第3章の2）との間でも相互に推論せず、第11条の5に定める。

### 第3条（点数の性質）
点数および TRL は評価尺度であり、成功確率・株価上昇確率・投資利益率では
ない。

### 第4条（用語の定義）

[名称は 2026-11-10 に C-1（案A）で確定]

1. **TRLレベル**: 資料の主題である技術・製品・候補物質について、根拠に
   基づいて判定する 1〜9 の段階（第3章）。スコアから換算しない。根拠が
   無い場合は「未確定」とし、数値は置かない。
2. **技術成熟度スコア**: 長期評価の項目 technology_readiness の 0〜100 点。
   TRL レベルとは別の指標であり、並記する場合はこの名称で区別する。
3. **候補**: 評価の単位となる資料（論文・治験登録・ニュース・開示等）。
   評価は候補に付くが、TRL と項目の対象は候補そのものではなく、候補が
   証拠となる技術・製品および企業である（第2章）。
4. **MRLレベル**: 資料の主題である技術・製品について、その製造の成熟を
   根拠に基づいて判定する 1〜10 の段階（第3章の2）。TRL や項目のスコア
   から換算しない。根拠が無い場合および当面の判定対象でない場合は
   「未確定」とし、数値は置かない。
5. **CRLレベル**: 資料の主題である技術・製品について、その商業化の
   成熟を根拠に基づいて判定する 1〜9 の段階（第3章の2）。TRL・MRL や
   項目のスコアから換算しない。根拠が無い場合は「未確定」とし、数値は
   置かない。

## 第2章 評価対象と証拠

### 第5条（評価対象）
1. TRL の対象は、資料の主題である技術・製品・候補物質そのものとする
   （企業全体ではない）。主題が複合システムの場合は、主要要素のうち
   最も未熟な要素に合わせる。
2. 企業固有の項目（収益化・財務的持続性・堀の持続性）は、対象企業が
   機械照合で strong（著者所属等）かつ一意に定まる場合にのみ採点する。
   定まらない場合は null とし、理由を不足情報に書く。

### 第6条（証拠の権威階層）
証拠は次の階層で扱い、上位の典拠を優先する。各項目の「根拠の質」は
この階層を参照する。
1. 規制当局・公的登録簿（EDINET、SEC EDGAR、治験登録、承認情報）
2. 査読論文・公的統計
3. 企業の公式開示・財務数値
4. 企業発表（PR TIMES 等）
5. 第三者報道

運用: 単一の企業発表（階層4）のみを根拠とする項目は 59 点を上限の目安と
する。同じ事実が企業発表と報道の両方で確認できる場合は強い根拠として
扱う。関連事業ニュースは見出しレベルの補助根拠であり、数値を推測で
補わない。関連財務根拠は技術項目の根拠に使わない。

### 第7条（不足の扱い）
1. 資料群の性質上、原理的に含まれない種類の情報（第三者機関の市場規模
   統計、競合との直接の定量比較、特許の明細、企業の将来予測等）が無い
   ことは、不足として数えず、null の理由にしない。各項目は資料内に
   ある代理指標で評価する。
2. 将来の出来事の結果を待つしかない不足（治験結果、承認審査、量産の
   継続実績等）は「結果待ち：」と明記し、通常の不足と区別する。
3. null には2つの意味がある: 根拠が未調査で無い場合と、段階的に
   存在しない場合（第5章の段階未達）。両者を混同しない。

## 第3章 TRL 判定規程

### 第8条（共通定義）
各レベルは「資料中に実施済みとして書かれている証拠」で決める。
[典拠: NASA の TRL 定義（Mankins 1995 ほか）を土台とし、本システムの
運用を加えたもの。補助典拠: EU Horizon Europe の TRL 定義、ISO 16290
（宇宙）、GAO/DoD の TRA ガイド]

- TRL 1: 基本原理が観察・報告された。
- TRL 2: 技術コンセプト・応用が定式化された。裏付ける実験・試作はまだ無い。
- TRL 3: 重要機能の概念実証（解析的・実験的）。数値や観測を伴う結果がある。
- TRL 4: 実験室環境で要素が検証された。
- TRL 5: 関連環境（実使用に近い条件）で要素が検証された。
- TRL 6: 関連環境でシステム／サブシステムが実証された。
- TRL 7: 運用環境（実使用そのもの）でシステム試作品が実証された。
- TRL 8: 実システムが完成し、試験・実証で認定された。
- TRL 9: 実システムが運用で実証された。実際の任務・事業・診療・サービス
  として使われ、実績がある。

### 第9条（判定手順）
1. 資料の主題の技術・製品・候補物質を特定する（企業全体ではない）。
2. 主題について、資料に「実施済み」として書かれた最も進んだ行為を特定
   する。計画・予定の行為は数えない。
3. その行為の段階をレベルとする。
研究論文・治験登録のように研究成果そのものが資料の場合は、主題が特定
でき研究内容が書かれている以上、原則として 1〜3 のいずれかに位置づける。
未確定（null）にしてよいのは、主題の技術が特定できない場合と、資料が
研究内容に触れていない場合に限る。

### 第10条（判定ルール）
1. 実施済みだけを数える。「計画」「予定」「目標」は証拠にしない。
2. 迷ったら切り下げる。上位レベルの証拠が部分的・間接的・曖昧なら
   下のレベルを取る。
3. TRL 3 以上には具体的な結果（数値・観測・症例・測定結果）が要る。
   主張だけの資料は TRL 2 止まりとする。シミュレーションのみの結果は
   TRL 3 を上限の目安とする。
4. TRL 9 は「繰り返し・継続」の証拠を必須とし、単一の成功だけでは
   TRL 9 にしない。確認事項はセクター別附則に従う。

### 第11条（セクター別附則）
各セクターの段階の読み替えとエッジルールは、評価プロンプト
（long.v4.md [セクター別の運用]）の現行文を正とし、本条には要点と
典拠のみを記す。全文の取り込みは起草の次段で行う [要作業]。

- **バイオ・医薬** [典拠: FDA / EMA / PMDA の開発フェーズと承認制度]:
  in vitro=3、in vivo=4、Phase 1=5、Phase 2=6、Phase 3=7、承認取得=8、
  市販後の実臨床データの蓄積=9。フェーズは記録の明記を根拠とし、推測で
  決めない。医療機器は臨床評価・承認で読み替える。
  **観察研究・レジストリの位置づけ**: 市販後観察研究やレジストリは、
  その対象製品の TRL 9 の証拠になり得る。ただし観察期間と実臨床データ
  の蓄積が明記されなければ TRL 8 にとどめる。観察研究という研究形式
  自体が段階を下げることはない（対象は研究ではなく製品であるため）。
- **宇宙** [典拠: ISO 16290]: 地上試験=4、耐宇宙環境試験=5、地上統合
  実証=6、軌道上実証=7、初回飛行成功=8、繰り返しのミッション成功=9。
  相乗りでの軌道実証は搭載物自身の 7 とし、輸送系の実証にはしない。
  政府採択・契約はそれ自体では段階を上げない。
- **AI・ソフトウェア**: 公開データでの検証=3、実データ検証=4、試行導入
  =5、複数先・継続試行=6、本番導線での試作運用=7、本番環境での性能
  実証=8、複数環境・長期間の継続実績=9。リリースや課金の開始自体は
  8 の根拠にしない。外部基盤モデルの成熟度は算入しない。規制領域では
  承認／認可が 8 の条件。
- **半導体・ハードウェア**: 概念実証=3、試作の評価結果=4、関連環境での
  動作確認=5、量産試作と信頼性試験=6、顧客製品への搭載実証=7、顧客
  認定と量産プロセスの再現性=8、量産環境での長期信頼性=9。テープアウト
  の発表だけでは 4 にしない。デザインウィンは 7 の根拠になるが、量産
  出荷だけでは 8 にしない（認定と再現性が条件）。
- **ロボティクス・産業自動化**: 要素実験=3、実験室検証=4、関連環境での
  動作=5、現場 PoC と実測=6、実生産ラインでの試行運用=7、量産モデル
  完成・顧客認定・安全規格適合=8、複数現場・長期間の本番稼働=9。
  展示会デモ・動画・シミュレーションのみは 5 を上限とする。
- **エネルギー・蓄電池** [典拠: UN 38.3 / IEC 62133 等の認証制度]:
  小型セル実測=3、実用形状セルの試作=4、実使用条件での検証と安全試験
  =5、パイロットライン工程検証=6、顧客製品での実証=7、量産ライン稼働
  と顧客認定=8、量産供給の継続とフィールド信頼性=9。実験室性能だけ
  では 4 を上限とする。「量産ライン建設中」は段階を上げない。
- **量子技術**: 要素の概念実証=3、小規模システムの実験室検証=4、外部
  利用可能な試作システム・実回線試験=5、誤り訂正の実証・顧客課題での
  試験利用=6、顧客環境での商用トライアル=7、商用システムの定常提供
  =8、複数顧客・長期間の有償利用継続=9。量子ビット数そのものは根拠に
  しない。政府契約・助成の採択は段階を上げない。
- **防衛** [典拠: 米 DoD の TRA と GAO-20-48G の読み替え]: 開発・試験
  の段階で判定し、採択・受注・輸出承認は商用展開として段階を上げない。
  TRL 9 は、配備先が複数であることと継続運用期間の明記を条件とする。
  運用文は long.v4.md [セクター別の運用] の防衛の項に置く。

## 第3章の2 MRL・CRL 判定規程

### 第11条の2（位置づけと出典）
1. MRL（製造成熟度）と CRL（商業成熟度）は、TRL と並ぶ独立の物差し
   である。いずれもレベル（段階の判定）であって項目のスコアではなく、
   総合点・帯域・二軸集計には含めない。事業軸の項目（収益化・市場
   成長・財務・競争優位）の採点とも混ぜない。
2. 典拠: MRL は米 DoD の MRL Deskbook（2025 年改訂版）、CRL は
   ARPA-E（米エネルギー省傘下機関）の Commercial Readiness Level
   定義による。ARENA の Commercial Readiness Index（1〜6）は、
   段階の粒度を取る判断により採用しない。
3. 判定の単位は TRL と同じく資料の主題である技術・製品であり、
   企業全体ではない。複合企業では、その製品に帰属する証拠だけで
   判定し、帰属できない企業全体の実績ではレベルを置かない。
4. MRL は本章で定義のみを置き、判定は材料の蓄積を待って別途開始
   する（開始までは評価は MRL を出力しない）。CRL は本章の施行と
   同時に判定を開始する。根拠は材料プールの実測（製造の証拠が
   構造的に薄く、商業の証拠には判定を始められる蓄積がある）に
   よる。設計の記録は ~/workspace/trl-readiness-levels/DESIGN.md。

### 第11条の3（MRL の定義と適用範囲）
各レベルは「資料中に実施済みとして書かれている証拠」で決める
（DoD MRL Deskbook の定義の要約）。

- MRL 1: 製造への含意が識別された。
- MRL 2: 製造コンセプトが識別された。
- MRL 3: 製造の概念実証ができた。
- MRL 4: ラボ環境でその技術を製造できる。
- MRL 5: 量産関連環境で試作部品を製造できる。
- MRL 6: 量産関連環境で試作システム／サブシステムを製造できる。
- MRL 7: 量産代表環境でシステム／サブシステム／部品を製造できる。
- MRL 8: パイロットラインの能力が実証され、低率初期生産を開始できる。
- MRL 9: 低率生産が実証され、全率生産を開始できる体制がある。
- MRL 10: 全率生産が実証され、リーン生産の実践が定着している。

適用範囲と Deskbook との差異:

- Deskbook の 9 スレッド（技術・産業基盤、設計、コスト・資金、材料、
  工程能力・管理、品質管理、製造人材、施設、製造管理・計画）による
  評価と「最も低いスレッドがレベルを決める」規則は採用しない。
  公開一次情報では大半のスレッドが観測できず、最低値規則を掛けると
  全件が最低段階に張り付くためである。判定は第9条の型（実施済みの
  最も進んだ行為の段階を取る）で行う。
- AI・ソフトウェアは製造が存在しないため対象外とする（配信基盤の
  規模は製造ではない）。
- バイオ・医薬では「製造」を CMC（原薬・製剤の製造プロセス、GMP
  適合、スケールアップ）に限定して読み、承認取得そのものは MRL の
  根拠にしない。プラットフォーム技術自体には MRL を立てない。
- TRL 附則（第11条）の半導体・エネルギー等の記述には量産プロセスの
  再現性など製造に触れる条件が含まれる。同じ証拠が TRL と MRL の
  両方を支えることがあるのは証拠の共有であり、相互推論ではない。

### 第11条の4（CRL の定義と判定）
各レベルは ARPA-E の定義による（要約）。

- CRL 1: 用途・ユースケース・市場の制約についての知識が限定的・
  偶発的、または未取得。
- CRL 2: 潜在的な用途・市場・競合技術への浅い理解がある。市場調査
  は二次情報中心で、製品アイデアは推測的・未検証。
- CRL 3: 用途・市場要件・競合の理解が進み、技術を製品として検討
  できる。製品仮説（ストローマン）が作られ、一次調査の比重が増す。
- CRL 4: 主たる製品仮説が特定され、潜在顧客との対話で磨かれる。
  価値提案が明確になり、基本的なコスト・性能モデル、競合分析、
  バリューチェーンの初期マッピング、認証・規制要件の特定がある。
- CRL 5: 対象市場への深い理解が得られ、製品が定義される。包括的な
  コスト・性能モデル、供給者・提携先・顧客との関係構築と製品定義
  への関与、包括的な競合分析、基本的な財務モデルがある。
- CRL 6: 市場・顧客ニーズと製品要件への翻訳が文書化される。提携が
  バリューチェーン全体で形成され、認証・規制対応が進行中である。
- CRL 7: 製品設計が完了し、供給契約と顧客契約が締結され、必要な
  認証・規制適合が済んでいる。
- CRL 8: 顧客認定が完了し、初期製品が製造され販売された。
- CRL 9: 広範な展開が達成された。

判定の運用（公開一次情報への翻訳）:

- CRL 1〜5 の中核は市場理解・製品仮説・モデル構築という社内の成熟
  であり、公開一次情報からは原則として観測できない。したがって
  レベルは、外部から観測できる「実施済みの到達点」でのみ置く。
  観測できる到達点が無い場合は、社内成熟を推測で埋めず未確定とする。
- 観測できる到達点の目安: 製品仮説と価値提案の具体的な公表と
  潜在顧客との対話の確認 = 4、共同開発・有償 PoC 等による顧客・
  提携先の製品定義への関与 = 5、提携の形成・認証対応の実施 =
  6、有償の供給契約・顧客契約の締結 = 7、当該製品の販売・提供の
  実績（販売開始・出荷・課金・売上） = 8、複数市場・複数顧客への
  継続的な展開 = 9。
- CRL 9 には「繰り返し・継続」の証拠を必須とする（原則2 の適用）。
  単一顧客・単一市場での販売だけでは 9 にしない。
- 研究開発契約・助成金の採択は事業化の契約ではないため 7 の根拠に
  しない。政府の調達契約は、供給・納入の内容を持つ場合に限り
  顧客契約として扱う。
- バイオ・医薬: 承認取得は TRL の段階であり CRL ではない。当該製品
  の販売開始・売上が確認できれば 8。ライセンス（導出）契約は顧客
  契約とは別扱いとし、導出先での販売実績が見える場合に限り 8 の
  補助根拠とする。
- 対象企業が strong で一意に定まらない場合は判定しない（企業固有
  の項目と同じ置き方）。

### 第11条の5（MRL・CRL の共通ルール）
1. 判定手順とルールは TRL の第9条・第10条を準用する（実施済みの
   行為だけを数える、計画・予定は証拠にしない、迷ったら切り下げる、
   レベルが整数のときは理由と根拠が必須）。
2. **相互推論の禁止**: TRL・MRL・CRL は互いに推論しない。TRL の
   高さから商業化の進展を、売上の大きさから技術の実証を、製造の
   成熟から市場の成熟を、それぞれ推測してレベルを置いてはならない
   （原則3 の拡張）。項目のスコアからレベルへの換算もしない。
3. 証拠が項目の採点（収益化等）と重なる場合は、同じ一次情報を
   それぞれの物差しで独立に読む。証拠の共有は推論ではない。

## 第4章 項目採点規程

### 第12条（長期評価の項目）
長期成長評価は次の6項目を 0〜100 点で採点する。採点アンカー（帯域の
定義）の全文は評価プロンプト（long.v4.md [採点アンカー]）を正とする。

1. technology_readiness（技術成熟度スコア）: TRL 相当の実証段階。
2. technological_advantage（技術的優位性）: 既存手段に対する定量比較の
   具体性で決める。
3. monetization（収益化能力）: 収益の実績で決める。TRL とは独立に
   評価し、TRL が高くても収益化の根拠が無ければ高得点にしない。
4. market_growth（市場成長性）: 市場裏付けの質で決める。資料内の代理
   指標（患者規模・適応の広がり等）でも評価する（第7条）。根拠には
   対象地域・対象期間・TAM/SAM の区別を求める。
5. financial_sustainability（財務的持続可能性）: ランウェイ（原資=
   現預金＋短期投資、burn=年間の純損失を主とし営業 CF マイナスが
   大きければそちら、1年以内に返済期限が来る債務は原資から差し引く）
   を目安に数値で決める。継続企業の前提に疑義の注記がある場合は
   0〜19 の帯域とする。財務数値が資料に無い場合は推測で付けず
   null とする。
6. moat_durability（堀の持続性）: 障壁の複合性で決める。特許の残存
   期間・規制上の独占・データ障壁の内訳で分解して見る。

TRL レベルと第1項の点数帯域の対応、および根拠が単一出所の場合の扱い
は次のとおりとする。いずれも監査で観測するに留め、点数の上書きも
保留（hold）もしない。
- レベルと点数帯の対応: 1,2=0〜19 / 3=20〜39 / 4=40〜59 / 5=40〜79 /
  6=60〜79 / 7,8,9=80〜100。対応を外れた評価は監査 A16 で観測する。
- 根拠がチェック済み一次情報の単一出所のみの項目は、59 を上限の目安
  とする（硬い上限ではない）。上限を超えた項目は constraint_codes に
  single_source を記録し、監査 A17 で観測する。

### 第13条（参考項目: 経営陣・実行力）
Payne スコアカード法で最大の重み（30%）を持つ「経営陣」は、本システム
の証拠プールでは観測範囲が限られるため、参考項目として新設する。
- 定義: 経営陣の経歴、過去の事業化・承認取得・提携の実行実績、経営陣の
  継続性、ガバナンス開示の範囲で採点する。
- 位置づけ: 採点し表示するが、総合点・軸別点・必須判定・不足判定には
  含めない。証拠が無ければ null とし、それを理由に hold しない。
- 格上げ（総合点への算入）は、証拠が実際にどれだけ得られるかを観測
  したうえで、別途改訂により判断する。
[実装: 2026-11-10 の A類バッチで実装済み。long.v2 に項目定義と採点
アンカーを追加し、scoring.json の long.reference に登録した
（config_version 2026.11.1）。export では config.reference_items として
同梱し、表示は詳細・ドロワーの「参考項目」に分離して不足の集計からも
外している。欠落した出力は検証でエラーにせず null として記録する]

### 第14条（イベント評価の項目）
今後1〜6か月のイベント評価は、長期評価と独立に次の6項目を採点する:
catalyst_quality（材料の質）、expectation_gap（市場予想との乖離）、
not_priced_in（未織り込み度）、timing_feasibility（時期の実現可能性）、
supply_demand（需給構造）、downside_resilience（下落耐性）。
市場予想や株価の裏付けが資料に無い場合、expectation_gap と
not_priced_in は null とする。ただし株価反応データ（材料の公開日を
挟んだ反応リターン・標準化反応・出来高倍率を決定的に計算したもの）が
資料にある場合は、その数値を乖離・織り込み度の根拠としてよい。
イベント自体も構造化して記録する（status 語彙: anticipated /
occurred / delayed / cancelled / completed、date_window、expectation /
actual の数値とその根拠 claim）。価格反応はコードが決定的に計算した
数値を正とし、評価側は転記しない。
アンカー全文は event.v3.md を正とする（v1・v2 は凍結）。
[本条の株価反応データの扱いは 2026-11-06 の event.v2 導入時に criteria
ページ側へ先に反映されていたものを、2026-11-10 に正本へ取り込んだ]

### 第15条（採点の共通ルール）
1. 根拠が無い項目は null とし、0 点で埋めない。null でない項目には
   理由と根拠（1件以上）が必須。反証も記録する。
2. 帯域に迷ったら、根拠の質が低い側の帯域を取る。
3. 前商業段階（TRL 3 以下）の技術では、事業項目は未成立が通常である。
   その場合は null とし「前商業段階のため未成立」と書く（第5章の
   段階未達として扱い、不足とは区別する）。
4. 保守的な減点は許容する。ただし減点の理由は、具体的にどの証拠が
   不足・不十分なのかに紐付けて書く。「証拠が弱い」「情報が限られる」
   等の漠然とした理由だけでは減点しない。不足の数え方は第7条に従う
   （原理的に含まれない情報は不足として数えず、結果待ちは区別する）。
   TRL レベルの判定理由についても同様とする。
   [2026-11-04 泰崇の指示で追加。2026-11-06 の決定により、プロンプトへは
   反映せず、担保は規則監査 A7 に一本化する（LLM の遵守能力への懸念から。
   プロンプト変更に伴う purge も回避できる）]
5. トレーサビリティとコード化（v3 世代）。抽出は claim の共通封筒
   （局所 ID・原文引用 quote・帰属 subject・kind・polarity・時点
   event_date/period・状態 status・関係 relations・数値 quantities・
   識別子 identifiers・領域 facet）で記録し、評価は根拠 claim を
   basis_claim_ids で指す。制約・減点・不足の理由はコード語彙
   （constraint_codes / deduction_codes / missing_codes）でも記録する。
   未知のコードは保存し、監査では未分類として扱う。複数の技術が混在
   する場合は技術ごとの TRL（trl_levels）を記録し、代表値は主題の
   技術の値とし、主題が定まらなければ最小値とする。

## 第5章 集計規程

### 第16条（二軸集計と段階未達）
1. 長期評価の総合点は、技術軸（technology_readiness、
   technological_advantage）と事業軸（monetization、market_growth、
   financial_sustainability、moat_durability）に分けて集計する。
2. TRL レベルが確定し、かつ 3 以下の場合、事業軸は段階未達
   （pre_stage）とし、技術軸が揃えば技術軸の総合点で確定（final）
   とする。このとき段階未達の事業項目は必須の不足に数えない。
3. それ以外の場合、総合点は全項目が非 null のときにのみ確定する。
   1つでも null なら hold とし、重みの再配分はしない。

### 第17条（重み）
重みは外部フレームワークを典拠とし、本システムの目的に合わせて
肉付け（分割・格上げ・新設）したものである。導出は次のとおり。

典拠（Payne スコアカード法、Angel Capital Association 2019 改訂）:
経営陣30 / 機会の大きさ25 / 製品・技術15 / 競合環境10 / 販売・提携10 /
追加投資の必要性5 / その他5。[補助典拠: MacMillan et al. 1985/1987 の
VC 判断基準研究（経営者・チームが最重要、次いで市場・製品・財務）、
ファクター投資の実証（収益性・品質・成長）]

| 本システムの項目 | 重み | Payne 対応 | 増減の理由 |
|---|---|---|---|
| 技術成熟度スコア | 30 | 製品・技術15 の分割 | 技術の立証が本システムの主対象のため最重みとする |
| 技術的優位性 | 15 | 製品・技術15 の分割 | 同上（分割の他方） |
| 収益化能力 | 20 | 販売・提携10 | 上場企業では実績で測れるため格上げ |
| 市場成長性 | 15 | 機会の大きさ25 | 技術と市場は分離する原則と、証拠の質（代理指標中心）に見合う重みへ抑制 |
| 財務的持続性 | 10 | 追加投資の必要性5 | ランウェイを開示数値で測れるため格上げ |
| 堀の持続性 | 10 | 競合環境10 | 特許・規制障壁まで具体化し同重み |
| 経営陣・実行力 | 参考項目 | 経営陣30 | 観測可能性の制約のため総合点には算入しない（第13条） |

（config_version 2026.11.0、commit 40318b1）。試行前の実測では、保存済み

### 第18条（帯域）
総合点の帯域は 0–19 極めて弱い / 20–39 弱い / 40–59 中程度・不確実 /
60–79 強い / 80–100 非常に強い とする（別表 scoring.json）。

## 第6章 方向性

### 第19条（direction）
direction は資料が示す材料の方向性（positive / negative / mixed）を、
点数や TRL とは独立に判定する。追い風の出来事（治験の進行・良好な結果、
承認、受注・提携・資金調達の成立、増収等）と逆風の出来事（中止・未達、
承認見送り、提携解消、減収等）のどちらが中心かで決める。全項目に点数が
付いたこと自体は positive を意味しない。

## 第7章 運用規程

### 第20条（スクリーニングと再評価）
1. 評価対象の選定条件（要旨の長さ、資料の鮮度、1実行あたりの評価件数
   等）は別表 scoring.json の screening に定める。
2. 再評価は原則として前回評価から14日後とする。ただし治験登録の更新
   のように、登録簿の変更自体が新しい証拠になる場合はこの限りでない。
3. 評価の生成に失敗した場合（形式エラー等）は、不足分を明示して1回
   だけ再生成する。

### 第21条（保持と削除）
資料の保持期間と削除（prune）の条件は実装に定める。辞書から外れた
別名による企業リンクは、実行の末尾で削除する（stale-link pruning）。

### 第22条（収集ソースの拡充方針）
収集ソースの追加は、権威のある出典を優先する。候補: 規制当局の承認
情報（FDA / EMA / PMDA）、EU の治験登録（EU CTR）、特許（J-PlatPat /
EPO）、公的採択（NEDO / AMED）。追加は実取得による裏取りと承認を
経て行う。

## 第8章 表示規程

### 第23条（ラベルの分離）
サイトでは TRL レベルと技術成熟度スコアを、名称と単位で区別して表示
する（例: 「TRL 9（9段階）」「技術成熟度スコア 85（100点満点）」）。
両者を同じ「技術成熟度」の名で並記しない。[未実装: 起草後に反映]

### 第24条（表示専用の分類）
企業のステージ分類（研究開発型／実証型／量産型／商業化型）とタグは、
表示・分析専用の分類であり、評価・選定には一切使わない。

### 第25条（翻訳の表示）
英語資料の日本語訳には、翻訳に使った API の出典を表示する。翻訳は
専用 API のみで行い、評価用 LLM は翻訳に関与しない。

## 第9章 改訂手続き

### 第26条（変更の分類）
本規程および実装の変更は、次の分類で効力を定める。
- **A1 類（再評価が必要な変更）**: TRL 定義・判定ルール・項目アンカー・
  必須項目・集計条件の変更。プロンプトまたは集計コードの変更を伴い、
  purge と再評価を行う。版を上げる。
- **A2 類（再計算のみで済む変更）**: 重み・帯域の変更。項目スコアは
  保存済みのため、LLM を使わず保存済み評価の一括再計算で効かせる。
  実装は `trl.py recalc`（既定は報告のみ、`--apply` で書換え）と、
  scoring.json の `recalc_on_run` を有効化した場合の実行時自動適用。
  再計算した評価には来歴（変更前版・旧総合点・旧帯域・日時）を残す
  （2026-11-02 実装）。
- **B 類（明文化）**: 現行運用を文章化するだけの変更。評価は変えない。
  purge は不要。
- **C 類（表示変更）**: ラベル・表示のみの変更。purge は不要。

### 第27条（版管理）
規程の版は評価の設定版（config_version）と対応づけて記録し、変更履歴を
本規程の末尾に残す。過去の評価がどの版で生成されたかは、評価レコードの
設定版と生成ハッシュで追跡できる。
